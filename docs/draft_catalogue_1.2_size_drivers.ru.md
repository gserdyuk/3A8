# ЧЕРНОВИК — каталог 1.2: драйверы размерных классов — ПРИМЕНЁН (перевод для ревью)

**Статус: ревью пройдено, применён 2026-08-21** как §3a (W10) каталога
`docs/technology_catalogue.md`. Исторический файл; авторитетен каталог. Решения автора по §10:
(1) пороги утверждены, **добавлен XL** (XL-элемент ценится по XL и репортится как вероятная грубость
модели по M10); (2) `U4` — брекетом; (3) `D2`/`D3` — брекетами, альтернатива-ставка остаётся
открытой заметкой измерения delivery; (4) у `statement` — **подкласс размеривания**
compliance / behavioural, классы W7 не тронуты.

Цель конструкции: свести суждение о размере к **пересчёту названных вещей**, чтобы два прогона
расходились видимо — на перечислении — или не расходились вовсе.

---

## 1. Правила

**R1 — один размерный класс на элемент, назначается один раз, используется всюду.** Размерный класс
`S / M / L` — свойство **элемента**, выводимое из его задекларированного содержимого и собственного
покрытия при закрытии модели. Каждая по-элементная активность на этом элементе по умолчанию берёт
класс элемента. Активности, чья стоимость масштабируется иначе, переопределяют его собственным
драйвером (§4) — это исключение, а не правило.

Зачем: это схлопывает поверхность суждений. Батчу из 25 элементов нужно ~25 подсчётов, а не ~150
догадок по позициям, и проектирование, тест-дизайн, реализация тестов и ревью одного элемента не
могут разойтись во мнении о том, насколько он велик.

**R2 — счёт через перечисление.** Обоснование размера — не число, а **перечисление**: «M — 3
действия: ранжировать предложения, переранжировать при изменении требования, объяснить ранжирование».
Счёт — это длина списка. Два разошедшихся прогона разойдутся на видимом, оспариваемом списке — та же
форма аудита, что у матрицы покрытия.

**R3 — несчитаемый драйвер — это дефект-репорт, а не догадка.** Если задекларированное содержимое не
даёт считать (голое имя, пустая декларация), прогон помечает элемент как *не поддающийся размериванию
— дефект модели (M10)* и класс не назначает. Молчание и размер «на глазок» одинаково вне закона.

**R4 — позиционные размеры вычисляются, а не судятся** (§5). Активности per-parent и once берут класс
из арифметики дерева — счёт поддерева, брекет модели, карта окружений. Ноль суждений, ноль разброса.

**R5 — пороги живут здесь, а не в прогонах.** Все пороги §3 — часть закреплённого каталога. Изменение
порога — бамп версии.

**R6 — драйвер считает объём, никогда — усилие.** Драйвер не может ссылаться на сложность, риск,
новизну или время. Это принадлежит ширине O–P тарифной таблицы и референсному классу — не
классификации.

## 2. Размерный класс элемента (R1)

Считается из задекларированного содержимого элемента плюс собственного покрытия, по классу элемента:

| класс элемента | что перечисляется | S | M | L |
|---|---|---|---|---|
| behaviour (поведение) | различимые действия (глагол над объектом), названные в содержимом | 1 | 2–3 | ≥4 |
| interface (интерфейс) | потребляемые/предоставляемые операции; названная забота протокола/аутентификации считается за одну | 1 | 2–4 | ≥5 |
| surface (поверхность) | различимые пользовательские задачи, которым служит экран (посмотреть X, ввести Y, утвердить Z) | 1 | 2–3 | ≥4 |
| store (хранилище) | виды сущностей, за которые хранилище отвечает | 1 | 2–3 | ≥4 |
| statement (утверждение) | системы или компоненты, которые ограничивает свойство | 1 | 2–4 | ≥5 |
| aggregate (агрегат) | — не размеривается: агрегат не получает по-элементного конструирования; его работа — позиционная (§5) | | | |

## 3. Использование класса элемента по умолчанию

Эти активности берут класс элемента **как есть** — без собственного драйвера:

- `K1` проектирование элемента · `K2` реализация · `K3` реализация утверждения
- `A2` тест-дизайн · `A3` реализация юнит-/компонентных тестов · `A4` код-ревью
- `F1` формальная спецификация · `F2` вывод обязательств доказательства · `F3` построение
  доказательства · `F4` ревью спецификации · `F6` инспекция поверхностей *(измерение A-FV тоже
  задрайверено, потому что фальсификационный тест — предсказание 2 — подставляет его, и оно должно
  быть оцениваемым)*

## 4. Переопределения на уровне активности (исключения, каждое с причиной)

| id | активность | что перечисляется | S | M | L | почему умолчание не годится |
|---|---|---|---|---:|---:|---|
| A8 | подготовка тестовых данных | элементы store + interface в поддереве родителя | ≤1 | 2–3 | ≥4 | объём данных следует за хранилищами и подачами, а не за собственным содержимым родителя |
| A9 | тестирование производительности/доступности | измеримые цели, названные утверждением (пороги, SLO) | 1 | 2–3 | ≥4 | одно свойство может нести несколько различных измерений |
| A10 | контрактное тестирование интерфейса | использует класс элемента-интерфейса | — | — | — | тот же счёт; перечислено для полноты |
| D4 | проработка требования | id требований в собственном покрытии элемента | 1 | 2–3 | ≥4 | проработка масштабируется по обязательствам, а не по размеру реализации |
| G1–G3 | спецификация / подготовка / сверка загрузочных данных | виды сущностей в хранилище, требующие предзагрузки (подмножество сущностей хранилища) | 1 | 2–3 | ≥4 | стоят только загружаемые сущности; наполняемые в рантайме — нет |
| U1–U3 | подготовка / поддержка / разбор UAT | элементы surface в поддереве родителя | 1 | 2–3 | ≥4 | UAT масштабируется по экранам под приёмкой, а не по листьям |
| O1 | пользовательская документация | элементы surface в поддереве родителя | 1 | 2–3 | ≥4 | то же |
| S2–S3 | пентест / устранение находок | элементы surface + interface во всей скрещиваемой модели | ≤5 | 6–12 | ≥13 | поверхность атаки, а не размер модели |

## 5. Позиционные классы — вычисляются, без суждений (R4)

| скоуп | класс берётся из | S | M | L |
|---|---|---|---:|---:|
| per parent (`A5`, `A6`, `A7`, `D2`) | листовые элементы в поддереве родителя | ≤3 | 4–8 | ≥9 |
| once (`A1`, `D1`, `D3`, `D6`, `E2`, `E4`, `E6`, `F5`, `O2`, `O3`, `S1`, `U4`) | элементы в скрещиваемом скоупе — брекет модели | ≤30 | 31–90 | ≥91 |
| per environment (`E1`) | фиксированная карта: dev = S, stage = M, prod = L | | | |
| `E3` промоушен, `E7` хостинг | число окружений в декларации | 1 | 2 | ≥3 |

Заметка про брекет модели на фоне run 19: HM19-OA1 (78 элементов) ценит once-позиции по M, HM19-OA2
(129) — по L. Структурный разброс протекает в once-слой **арифметикой** — это задуманное поведение, а
не утечка.

## 6. Активности одного размера

Некоторые активности не масштабируются ничем считаемым и получают в таблице **одну строку**, без
классов: `O4` release notes · `U1d` production verification checklist · `U4` acceptance record
*(перенесён сюда из брекета, если автор предпочтёт; помечено как решение)*.

## 7. Циклы

Без изменений: число циклов — параметр декларации. Драйвер размеривает **один цикл**; `× cycles`
умножает позиции, но не класс.

## 8. Что остаётся суждением после этого черновика, честно

1. **Само перечисление** — что считать одним действием / операцией / сущностью. R2 делает его видимым
   и оспариваемым, но не механическим. Это остаточная свобода шага 4, и «≥90% тождественных позиций»
   из P1 — зарегистрированный тест того, что она мала.
2. **Классификация элементов** (behaviour против statement и т.д.) — наследуется от `Hotyn-W`, уже
   измерена: 74/77, три границы с последствиями.
3. Больше ничего. Цены — таблицы; счёт родителей, поддеревьев, окружений — арифметика.

## 9. Замечание о контаминации

Драйверы и пороги писались со знанием выходов run 22. Пороги — это счёт объёма, не усилий, так что
поверхность якорения мала — но проверка дешёвая, и ею стоит воспользоваться: **автор тарифной таблицы
(gap-blind) видит этот файл и вправе возразить против любого порога как не поддающегося оценке — до
записи значений.** Возражение — находка о драйверах, а не о таблице.
