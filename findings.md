# Findings — накопленные выводы по проекту 3A8

Рабочий лог инсайтов и эмпирических находок, на которые опирается METHODOLOGY.md. Не дублирует методологию, а фиксирует *почему* она сделана именно так — источники, эксперименты, открытые вопросы.

## 1. Почему нельзя просто спросить одну LLM несколько раз (single-model diversity problem)

- Классический Wideband Delphi работает за счёт независимости *экспертов-людей* — разного опыта и разной информированности. У одной модели в разных сессиях нет структурной независимости: "потолок незнания" систематический, а не случайный.
- Persona-промптинг (разные "роли" одной модели) даёт разнообразие фокуса, но не разнообразие аппарата мышления — под капотом один и тот же статистический механизм.
- **Эмпирическое подтверждение (anchoring bias у LLM сильнее, чем у людей):** реплика классического эксперимента Йоргенсена и Халкьельсвика на GPT-4, Llama 3.1, Gemini 1.5 Pro показала, что при смене формулировки вопроса ("сколько нужно на X" vs "сколько успеете за Y часов") оценки LLM расходятся **минимум в 6 раз сильнее**, чем у людей в оригинале. Для GPT-4: 4000 vs 150 рабочих часов на одном и том же наборе user story — то есть якорение почти полностью подавляет содержательный сигнал задачи. (Çalıklı & Alhamed, FSE 2025)
- Вывод: варьирование промпта/формулировки — не источник независимого мнения, а управляемое якорение. Если строить multi-persona debate, критично держать формат вопроса одинаковым для всех персон.
- LLM ведут себя не как люди даже там, где ожидалось сходство: сравнительные (парные) суждения не даются LLM легче прямых оценок, хотя у людей это так. Значит debias-техники, работающие для людей (сравнение вместо абсолютной оценки), нельзя переносить на LLM автоматически.

## 2. Три разных типа "незнания" — где LLM сильнее людей, а где нет

- **Breadth problem (широта охвата паттернов)** — LLM реально сильнее команды людей, видела на порядки больше post-mortem'ов и паттернов проектов.
- **Calibration problem (вес известных рисков)** — не факт, что LLM сильнее; RLHF тянет к "сбалансированным" ответам, что может систематически занижать вес хаотичных организационных факторов.
- **Локальное/тацитное знание** — данные, которых нет в природе текста (конкретно эта команда, конкретно этот человек, конкретно этот легаси-сервис). Никакой LLM и никакой метод оценки в принципе не покрывает — только живые люди с историей именно в этой организации.

## 3. Multi-agent debate — единственный LLM-native подход с независимым эмпирическим подтверждением

- SEEAgent (Bui et al., 2025) — мультиагентный фреймворк, где LLM-агенты дают оценки, обосновывают их и обсуждают с другими агентами/людьми до консенсуса. Превзошёл state-of-the-art методы по большинству метрик на реальном датасете; практики оценили опыт совместной работы положительно.
- Это прямое эмпирическое подтверждение того, что связка *persona + reference-class + multi-agent debate* — не только теоретически разумна, но и работает на практике.

## 4. Ключевой сдвиг: разные техники вместо разных экспертов ("expert с разным аппаратом")

Вместо декорреляции через людей — декорреляция через математически разные методы. Их слепые пятна не эмпирически случайны (как у людей), а **гарантированы конструкцией метода** — то есть предсказуемы заранее.

| Метод | Сильная сторона | Структурное слепое пятно |
|---|---|---|
| Decomposition (bottom-up + PERT) | Специфика конкретной задачи | Корреляция рисков между задачами; системные/интеграционные риски; overhead |
| Reference class forecasting | Системные риски целиком ("outside view") | Специфика именно этой задачи/команды |
| Throughput Monte Carlo | Организационный overhead и фрагментация — эмпирически, автоматически | Не объясняет причины; требует истории; предполагает похожесть будущих задач на прошлые |
| Parametric (COCOMO-подобные) | Независимость от субъективного суждения | Качество = качество калибровки; модели устаревают |
| ML/регрессия на истории | Семантические паттерны похожих задач | Объяснимость; новые типы задач вне выборки |

Дополнительно упомянутые, но не включённые в основной пайплайн: относительная оценка / planning poker (устойчивее к якорению у людей, но не факт, что у LLM — см. п.1), вероятностный PERT с учётом корреляции рисков.

## 5. Наблюдение про Scrum-overhead (спринты) → throughput как естественный корректор

- Личное наблюдение: много времени уходит на (a) старт спринта, (b) сдачу/ревью, (c) неутилизируемые "огрызки" времени.
- Это соответствует известным концепциям: "focus factor" в Scrum, "flow efficiency" в Kanban/Lean. Пункт (c) — по сути bin-packing проблема, статистически неизбежна при гранулированных задачах и фиксированной ёмкости спринта.
- Throughput Monte Carlo автоматически учитывает это эмпирически (из факта прошлых спринтов), decomposition — принципиально не может, потому что overhead не привязан к конкретной задаче.
- Существует отдельная исследовательская линия — agent-based/system dynamics моделирование поведения разработчиков (SPSM — Software Process Simulation Modeling): исторически доминируют discrete-event и system dynamics подходы; agent-based кейс (AVL) предлагает "практическую функцию эффорта" для моделирования поведения разработчика, включая прерывания на менторство и т.п. Результаты "выглядят многообещающе, но нужна ещё работа" — то есть рабочее направление, не готовый продукт.
- Классика жанра — Abdel-Hamid & Madnick, "Software Project Dynamics" (1991): system dynamics модель с эффектом Брукса, ramp-up новых сотрудников, накоплением необнаруженного rework, влиянием давления на качество.
- Практический вывод: для чистой оценки "сколько времени" достаточно простого поправочного коэффициента (реальный throughput / номинальная ёмкость за N спринтов). Полноценная поведенческая симуляция оправдана только для вопросов "что если" (сравнение сценариев организации работы), не для точечной оценки.

## 6. Проблема конвергенции при межметодном подходе

- В человеческом Delphi конвергенция — результат того, что *эксперт* меняет *своё* мнение после новой информации. У разных техник оценки это невозможно: метод не может "передумать" и начать учитывать то, что не учитывает по конструкции.
- Конвергенцию нужно инженерить явно, отдельным механизмом:
  1. **Независимые прогоны** — каждый метод даёт диапазон + assumption log.
  2. **Диагностика расхождения** — не "чьё число вернее", а какое конкретно слепое пятно объясняет разницу.
  3. **Перенос параметров** — механическая калибровка, не согласие мнений (пример: throughput → overhead-коэффициент как явный множитель к decomposition).
  4. **Финальный диапазон с объяснённым остатком** — то, что не устранилось переносом параметров, это честная мера неопределённости, а не шум для усреднения.
- **Важно:** полная конвергенция после явных коррекций не всегда успех — если методы отвечают на структурно разные вопросы, а сошлись в одну точку, это либо совпадение, либо один метод силой продавлен под другой и потерял диагностическую независимость.

## 7. Нужны ли исторические данные для сравнения decomposition vs reference class?

**Нет.** Reference class forecasting у LLM не требует внешнего датасета в контексте — референс-класс "размазан" по весам модели из тренировочных данных, в отличие от человека, которому нужен личный/командный опыт. Внешние исторические данные обязательны только там, где метод *по конструкции* не может работать без них: throughput Monte Carlo (нужна статистика реальных спринтов) и параметрические модели (нужна калибровка).

→ Практическое разделение работы: **Фаза 1** — decomposition + reference class прямо в разговоре с LLM, без датасета. **Фаза 2** — throughput/parametric, для которых датасет обязателен.

## 8. Источник исторических данных (для Фазы 2) — TAWOS

- TAWOS (Tawosi et al., MSR 2022) — датасет issues из открытых agile-проектов на Jira, 508,963 issues, 44 проекта, с реальными story points, resolution time, sprint-историей.
- **Ограничение:** сам датасет — MySQL-дамп на UCL Research Data Repository (rdr.ucl.ac.uk), недоступен из песочницы (не входит в разрешённые сетевые домены). Доступна только агрегированная статистика из самой публикации (Table 1).
- Пример агрегата — Spring XD (ключ XD): 3,707 issues, 66 спринтов, 610 багов, 31 разработчик → ~56 issues/спринт в среднем (без данных о дисперсии по спринтам).
- Открытый вопрос: где взять гранулярные (по-спринтовые) исторические данные — TAWOS в полном виде недоступен технически, у автора проекта также нет доступа к истории спринтов ни по одному реальному проекту на момент разговора (EPAM — доступ не подтверждён).

## 9. Первая ручная проверка Фазы 1 (BMS, 2026-07-17) — выводы

> Анекдот ~1982 г.: решали уравнение Шрёдингера для частицы на поверхности, задача распалась на 100+ интегралов. 
«Если мы не знали, как взять интеграл — мы им пренебрегали». 
— Точная модель слепого пятна decomposition: чему нет строки в WBS, тем пренебрегли, 
а сумма оставшегося выглядит строгой. 
Отличие хорошей практики от плохой — не в отсутствии пренебрежений, а в поимённом списке выброшенных интегралов 
(assumption log). 
Reference class — «эксперимент», меряющий сумму целиком, включая интегралы, которые никто не умеет брать.

Прогон на примере examples/BMS (РФП на booking management system, EPAM 2016). Артефакты: assumptions.md, run1_decomposition.md, run2_reference_class.md, run3_diagnosis_calibration.md.

- **Методология отработала как задумано:** decomposition дал 486 pd (и абсурдно узкий CI ±3.5% — предсказанный артефакт независимости), reference class — P50 950 pd с толстым хвостом (P90 1800). Расхождение ×1.95 разложилось по слепым пятнам практически без остатка (объяснено ~93% зазора центров); хвосты не сошлись — и не должны были.
- **Протокол независимости прогонов:** в одной LLM-сессии второй метод неизбежно заякорен результатом первого (см. п.1). Рабочее решение — каждый метод выполняет изолированный агент, получающий только вход (РФП + assumption log) без чужих результатов. Это обязательное требование пайплайна, не опция.
- **«Умножить и добавить» (инсайт автора):** межметодная калибровка Шага C — не один скаляр. Часть разрыва — статьи расходов, которых в WBS нет вовсе (чистые добавки), часть — таргетированные множители на подмножество пунктов (интеграции), часть — глобальные множители (scope creep, координация). Аффинная модель y=ax+b неидентифицируема по одной точке (нужно ≥2 проектов) → в Фазе 1 параметры не фитятся, а переносятся поимённо из внешних base rates; фит возможен только в Фазе 2 на собственной истории.
- **«Интеграция частей не стоит ничего» (инсайт автора):** сумма листьев WBS не содержит слагаемого за стыковку частей между собой — оцениваются узлы дерева, а платить приходится и за рёбра, которых ~n²/2 при n узлах. Это уточнение слепого пятна из METHODOLOGY §2: не «интеграционный риск» (вероятностный), а детерминированная статья расходов, у которой структурно нет строки в WBS. Пункты типа «интеграционное тестирование» маскируют проблему, но оцениваются по ощущению, а не из числа стыков — само число стыков из WBS не видно. Reference class закрывает это автоматически: в фактах завершённых проектов интеграция уже оплачена.
- **Предложенная поправка метода — integration-aware bottom-up (идея автора):** на каждом узле агрегации WBS (где k компонентов складываются в целое) добавлять явный интеграционный пункт, выводимый из фактического числа и типа стыков между детьми узла (по архитектурной диаграмме), а не «по ощущению». Цена одного стыка — переносимый параметр (base rates: system integration ~15–30% компонентной разработки; в Фазе 2 — мерить на истории). Оговорки: (а) двойной счёт с пунктами типа «интеграционное тестирование» — их надо худеть; (б) лечит только одно слепое пятно — overhead, scope creep и корреляция рисков остаются, полной конвергенции с reference class быть не должно. Проверяемое предсказание для BMS: пересчёт даст заметно >486, но <884 pd. **Статус: эксперимент проведён (run4_integration_aware.md), предсказание сбылось** — при ставке 15–20% на узел итог 568–602 pd (центр ~585, +20% к плоскому WBS; QA-пункт урезан против двойного счёта). Оставшийся разрыв до 884 — ровно непокрываемые поправкой пятна (scope creep, координация, внешние айсберги). Важное различение: внешние айсберги (чужие API хуже документации) и внутренние рёбра (наша сборка) — разные статьи; поправка переносит вторую из «множителя координации» в структурно выводимую строку.
- **Непреднамеренная кросс-валидация:** изолированный reference-class-агент независимо назвал типовой диапазон RFP-бидов класса (400–700 pd), и decomposition попал в него (486). Т.е. decomposition воспроизводит поведение типичного бида, а разрыв с классом — систематика стадии RFP, не дефект конкретного WBS.
- **Хвост не калибруется:** P90 класса (×1.8 к откалиброванному P90 decomposition) не достижим никакими множителями на WBS — хвостовые события не существуют как пункты WBS. Для контрактных решений (fixed price vs T&M, буферы) годится только reference class.

## 10. Второй ручной прогон (FaxRxTx / Venali, 2026-07-17) — первая сверка с фактом

Реальный проект 2007–2009: rewrite кор-функционала fax-платформы Venali (воркеры рендеринга/OCR, кластер с самодельной оркестрацией вочдоги+токены, NOC, портал). Артефакты: examples/FaxRxTx/ (SYSTEM.md, assumptions.md, run1–run4, FACT.md). Факт по памяти участника: **~120 чел-мес ±20%** (окно 96–144). Протокол слепоты: факт запечатан в FACT.md, ни оценщики, ни диагност его не видели; вскрытие — только на шаге D.

- **Результаты:** сырой decomposition E≈112; reference class P50 160 (P10 85 … P90 320); калиброванный decomposition 155 (135–180), диагност объяснил ~90% зазора центров с проверкой на двойной счёт.
- **Главный вывод — скромный, по настоянию автора:** воспоминания нечётки, и расхождение калиброванной оценки с фактом (+29% от центра окна, +8% от его края) лежит в пределах одной ширины погрешности самого воспоминания — по памяти отличить 12 месяцев от 13–14 нельзя. Поэтому утверждается только: **все три оценки согласуются с фактом в пределах точности измерителя; пайплайн не выдал абсурда ни на одном шаге.**
- **Оба структурных паттерна BMS воспроизвелись:** абсурдно узкий CI сырого decomposition (±8%) и некалибруемый правый хвост (выше ~177 pm множителями не дотянуть — резерв только из reference class).
- Зазор центров ×1.43 против ×1.95 в BMS: WBS здесь был «воспитанным» — вникание в домен, интеграционные тесты на живом трафике, QA/PM и часть рёбер уже сидели листами.
- **Гипотезы на будущее (не выводы):** (а) калибровка к P50 класса должна систематически завышать на проектах лучше медианы → форма ответа — тройка «центр из WBS, коридор из калибровки, резерв из хвоста класса»; (б) ансамблевые глобальные множители поверх воспитанного WBS — риск двойного счёта, возможна «скидка на воспитанность». Обе проверяются только на проекте с задокументированным (не по памяти) фактом.

## 11. Механика калибровки и проблема приведения проектов класса «один к одному» (обсуждение 2026-07-17, по следам FaxRxTx)

Три связанных вопроса, разобранных после закрытия примера FaxRxTx. Фиксируются подробно, потому что вместе образуют мост от Фазы 1 к Фазе 2.

### 11.1. Как именно происходит калибровка decomposition по reference class (шаг C)

Калибровка — **не** сдвиг оценки decomposition к числу класса и не усреднение. Последовательность (на цифрах FaxRxTx run3):

1. **Фиксируем зазор.** Сырой decomposition E=111.6, P50 класса 160 → зазор 48.4 pm. Reference class сообщает только масштаб недостачи, но не говорит, *где* в WBS она сидит.
2. **Раскладываем зазор по известным слепым пятнам decomposition** (они статичны, известны до всякого прогона): работы без строки в WBS; интеграционные рёбра (оцениваются узлы, платят и за стыки); организационный overhead; scope creep. Это шаг B: не «чьё число вернее», а «какое пятно объясняет разницу».
3. **Ставку каждой статьи берём из внешних base rates, а не из зазора.** Ключевая дисциплина: числа типа «scope creep ~10%», «переделка распределённого ядра ×1.3–1.5» приходят из общего знания о классе проектов и НЕ подбираются так, чтобы сумма сошлась с P50 класса. Почему нельзя подгонять: точка одна, поправочная модель — по сути y=ax+b, по одной точке a и b неидентифицируемы; подгонка дала бы иллюзию точности.
4. **Применяем поправки к WBS тремя типами** (таксономия «умножить и добавить» из п.9): чистые добавки (unknown unknowns домена +8.8, недостающие рёбра +3.6); таргетированные множители на подмножества листьев (ядро ×1.4 → +6.6, стабилизация рендеринга ×1.25 → +2.9, сходимость с v1 ×1.35 → +3.3); глобальные множители (scope creep 10% → +12.3, орг-налог 4% → +6.0). Обязательная проверка двойного счёта: пятна, уже закрытые листами WBS (в FaxRxTx — вникание в домен, живые интеграционные тесты, QA/PM), поправок не получают.
5. **Сверяем объяснённую долю.** +43.5 из 48.4 → ~90% зазора объяснено, калиброванный центр ≈155; остаток ~5 pm остаётся неатрибутированным — это мера неопределённости, а не шум. Близость 155 к 160 — результат проверки, не цель; объяснение половины зазора тоже было бы валидным итогом.

Конвергенция механическая, не эпистемическая: ни один метод «не передумал». И калибруется только **центр**: хвост (P90=320) недостижим множителями — хвостовые события не существуют как пункты WBS (воспроизведено в обоих примерах).

### 11.2. Как проекты одного класса приводятся «один к одному» (у одного сайта 10 страниц, у другого 5)

Разнородность внутри класса — центральная слабость reference class. Три способа приведения:

1. **Нормировка на собственную оценку проекта** (канонический, Флювбьерг): класс хранит не абсолютные трудозатраты, а **отношения** факт/оценка. Размер сокращается сам: у сайтов на 10 и на 5 страниц разные bottom-up оценки, но множитель перерасхода берётся из одного распределения. Именно поэтому пара «decomposition + reference class» стыкуется: WBS даёт проектно-специфичный якорь (он видит и страницы, и 2FA), класс — распределение множителя поверх якоря.
2. **Нормировка на единицу размера** (параметрический путь): функциональные точки, экраны, KLOC; класс даёт стоимость единицы ± разброс. Требует калиброванных исторических данных — в Фазе 1 недоступно.
3. **Сужение класса размерной полкой** (самый грубый; то, что неявно сделал run2, давая абсолютные P10/P50/P90): не «все rewrite», а «rewrite распределённой платформы *среднего* масштаба». Часть разнородности убирается условиями отбора; оставшаяся (2FA есть/нет) **никуда не девается — она остаётся внутри разброса P10–P90**. Ширина вилки класса — честная цена внутриклассовой разнородности; узкий reference class — подозрительный reference class.

Следствие: специфика «10 страниц против 5» — по определению слепое пятно класса и зрячая зона decomposition. Класс отвечает за форму распределения, положение точки внутри него определяет bottom-up. В Фазе 2 самый чистый вариант — способ 1 на собственной истории: распределение «факт / наша же decomposition-оценка» по завершённым проектам; нормировщиком каждого проекта служит его собственная оценка, и вопрос сравнения размеров исчезает по построению. Шаг C Фазы 1 — ручная поимённая аппроксимация этого множителя, пока истории нет.

### 11.3. Направление для Фазы 2: масштаб проекта как ковариата множителя

Идея: улучшить способ 1, сделав множитель перерасхода **функцией размера**, а не константой класса.

- **Эмпирическое основание:** большие проекты перерасходуют сильнее и с более толстым хвостом (COCOMO: показатель степени >1 при размере; данные Флювбьерга; статистика провалов — малые проекты успешны чаще). Значит от размера зависит и центр, и ширина хвоста → улучшается не только оценка, но и размер резерва.
- **Метрика размера уже есть бесплатно:** сумма decomposition-оценки ΣE — готовый прокси размера, доступный в момент оценки. Калибровка превращается из «умножь на константу» в «умножь на f(размер)». Связь с п.9 («умножить и добавить»): y=ax+b неидентифицируема по одной точке; с ковариатой размера по 2–3 проектам оценивается наклон, по 5–10 — кривизна.
- **Структурное обоснование, почему множитель обязан расти с масштабом** — интеграционные рёбра из п.9: узлов n, стыков ~n²/2; сумма листьев растёт линейно, недостача за рёбра — быстрее → зазор «WBS против факта» в процентах больше у крупных проектов. Показатель степени >1 выводится из структуры, а не из подгонки.
- **Цена — данные:** обусловливание режет выборку; на 5–15 собственных проектах свободная регрессия переобучится. Практичный компромисс — та же дисциплина, что в шаге C: форму зависимости (степенной показатель) брать извне как prior (COCOMO-класс), на своей истории подстраивать только уровень.

### 11.4. Поправка автора к 11.2–11.3: самонормировка не спасает, потому что размер меняет состав работ

Наблюдение автора: внутри «класса всех веб-сайтов» проекты на 5, 30 и 100 страниц — **разные классы**, хотя бы потому, что распределение работ в них разное. Значит «самонормирование» (способ 1 из 11.2) само по себе — не выход.

Разбор: размер даёт два разных эффекта, и лечатся они по-разному.

1. **Гладкий** — множитель перерасхода растёт с размером при том же составе работ (рёбра ~n²/2, координация). Это лечится ковариатой f(размер) из 11.3.
2. **Структурный (глубже)** — на каком-то размере появляются целые категории работ, которых у малого проекта нет вообще: CMS вместо вёрстки, информационная архитектура, выделенный PM, staging-контур. Это не множитель на существующие листья, а **новые ветки WBS**. Отношения факт/оценка в разных размерных режимах берутся из разных генеральных совокупностей — деление на собственную оценку этого не чинит.

**Следствия:**
- Способы 1 и 3 из 11.2 — не альтернативы, а обязательная последовательность: сначала стратификация по размерному режиму (полка — условие корректности, а не «грубость»), самонормировка валидна только внутри страты. Пулинг разноразмерных проектов в одно распределение множителя — ошибка спецификации класса, а не недостаток данных.
- **Операциональный критерий границы режима** (бесплатный, из уже имеющегося инструмента): два проекта в одном классе, если их WBS структурно подобны — совпадает набор веток, а не суммы. Появление у большего проекта веток, отсутствующих у меньшего в принципе, — маркер смены класса. Decomposition получает вторую роль: не только источник центра, но и тест принадлежности к референс-классу.
- Цена для Фазы 2: стратификация режет малую историю (5–15 проектов → 2–3 страты по горстке точек) → внешние prior'ы нужны на каждую страту отдельно; своя история подстраивает только уровень внутри страты.

### 11.5. Предосторожность: градиент к ML-модели (обсуждение 2026-07-17)

Наблюдение автора: цепочка улучшений 11.2 → 11.4 (самонормировка → ковариата размера → стратификация → prior'ы → подстройка уровней) — это постепенное сползание к построению ML-модели. Фиксируется **не как правило, а как предосторожность**: такое рассуждение есть, и усложнения/изощрённости нужно избегать.

Суть опасения:

- Методы лежат на одном континууме сложности: reference class — непараметрическая модель с одним категориальным признаком («класс»); COCOMO — плюс ковариата размера; ML-регрессия — то же с большим числом признаков и гибкой функцией. Пройдя градиент до конца, мы незаметно превращаем reference class в пятый метод из METHODOLOGY §2 — с его слепыми пятнами (необъяснимость, провал вне выборки) и без его честного названия.
- Для 3A8 это опасно особо: ценность фреймворка — в декорреляции слепых пятен *разных* датчиков. Дообогащённый до фитованной модели reference class перестаёт быть независимым датчиком; диагностика шага B питается расхождением, а одна изощрённая модель даёт одно число со скрытыми допущениями — то, от чего фреймворк уходил.
- Практическая ловушка: на 5–15 проектах модель не обучится, но выглядеть будет строго и сузит интервалы по построению. Широкая вилка класса — фича (честная мера разнородности, 11.2), изощрённая модель уничтожает её первой.

Ориентиры (не правила): датчики держать грубыми, сложность допускать только в слое диагностики (шаги B/C); за центр отвечает калиброванный decomposition, за хвост — сырые квантили класса (хвост фитованием не улучшается — квантилям нужны точки, а не параметры); лакмус — если «улучшение» требует что-то фитовать на собственной истории, пересечена граница метода, и честнее оформить это отдельным датчиком, чем растворить в существующем.

### 11.6. Первая проверка на данных (mars_model, 2026-07-17): что подтвердилось, что опровергнуто

Гипотезы §11.3–11.4 проверены на открытых датасетах PROMISE (China n=499, Kitchenham n=145, Desharnais n=81, Maxwell n=63). Метод — «MARS-лайт» по дисциплине §11.5: степенной фит в log-log, один хинж с перебором узла, AICc, бутстреп; плюс пилот «состав как параметры». Артефакты: mars_model/ (data/, fit_piecewise.py, composition_china.py, results.md, loglog_fits.png).

**Опровергнуто (с оговорками):**
- «Показатель степени b>1 у Effort~Size^b» — во всех четырёх датасетах b≤1 (0.67–0.98), в трёх CI целиком ниже 1: производственная функция показывает *экономию* масштаба. Это известный спор в литературе (Banker & Kemerer 1989; Kitchenham 2002): FP-датасеты дают b<1, KLOC-калибровки COCOMO — b>1. Оговорки: survivorship (в датасетах только завершённые проекты — хвост класса ненаблюдаем), смешение организаций, эндогенность (большим проектам — лучшие команды).

**Подтвердилось:**
- **Множитель перерасхода растёт с размером — хвостом, не центром** (Kitchenham, единственный датасет с парой «первая оценка/факт»): медиана Actual/FirstEstimate ≈ 0.97 во всех терцилях размера, а P90 растёт 1.11 → 1.15 → 1.46; наклон log(ratio)~log(size) положителен, CI не накрывает ноль. Точная формулировка §11.3 — про ошибку оценивания — верна.
- **Надбавка за интерфейсы поверх размера** (пилот состава на China): доля Interface-элементов значимо удорожает проект при том же AFP (+10 п.п. доли → ×1.10), причём поверх того, что FP-методика уже платит интерфейсам повышенным весом (в таблице весов IFPUG элемент EIF стоит 5–10 очков против 3–6 у обычного входа). Недооценка стыков переживает даже явную попытку заплатить за них повышенным весом.
- **Изломы существуют, но границы неустойчивы:** направление везде одно (наклон после узла растёт — экономия масштаба на крупных кончается), формально оправдан излом только в однородном Kitchenham (~600–700 FP, 98% бутстрепа согласны); в смесях организаций узел гуляет на порядок. Стратификация §11.4 осмысленна, но границы страт надо брать из однородной популяции (своей истории), не из чужих смесей.

**Поправка к теории (важная):** §11.3 смешивал две величины. Производственная функция Effort(Size) может показывать экономию масштаба; ошибка оценивания (факт/оценка) с размером растёт — хвостом при стабильной медиане. Для 3A8 релевантна вторая: пайплайн калибрует оценки, а не производит проекты. Аргумент рёбер n²/2 уточняется: **рёбра бьют не по стоимости проекта, а по её видимости в WBS** — у больших проектов больше невидимых статей, которые иногда выстреливают; отсюда «хвост толстеет, медиана стоит» — ровно наблюдаемая картина.

**Полученные модели** (China: E≈27·AFP^0.77; Kitchenham: E≈37·AFP^0.67 с изломом ~700 FP; и др., R² 0.44–0.63) — легальны только как **форма prior'а** (§11.5): переносится порядок степени, существование излома, рост хвоста множителя; уровень подстраивается на своей истории.
