# BMS — Прогон №1: Decomposition (bottom-up + PERT)

Дата: 2026-07-17. Вход: [BMS_extracted.md](BMS_extracted.md) + [assumptions.md](assumptions.md).
Правило прогона: WBS строится **строго по написанному в РФП** — без поправок на scope creep, «айсберги» и организационный overhead. Это не небрежность, а дисциплина метода: его слепые пятна должен ловить reference class, а не скрытые фаджи внутри WBS.

## Итог метода

- **E(total) ≈ 486 person-days** (~97 person-weeks).
- σ при допущении независимости пунктов ≈ 17 pd → 90% CI ≈ **458–514 pd**.
- Наивные границы (сумма всех O / всех P): **296–764 pd** — реальная неопределённость метода лежит ближе к этому диапазону, чем к CI (см. ниже).

⚠️ **Диагностический артефакт, ожидаемый методологией:** CI ±3.5% абсурдно узок. Он получается из допущения независимости ошибок между пунктами WBS — а это ровно слепое пятно №1 метода (корреляция рисков). Если проект «поплыл» на интеграции CTC, он почти наверняка плывёт и на агрегаторе, и на UAT. Узость CI — не точность, а следствие конструкции. В Шаге B сравнивать с другими методами надо и центр (486), и форму разброса.

## Assumption log метода (статические слепые пятна, по METHODOLOGY.md §2)

Не учтено **по конструкции**:
1. **Корреляция рисков между пунктами** — суммирование σ² предполагает независимость; общие причины (недоступность API заказчика, качество документации CTC, текучка) бьют по многим пунктам сразу.
2. **Системные/интеграционные риски целиком** — WBS покрывает написанное в РФП; «айсберги» типа реальной сложности «intelligent search» или недокументированного поведения CTC API в WBS не существуют.
3. **Организационный overhead** — ceremony, фрагментация времени, согласования с заказчиком, ожидание доступов. В pd-оценках пунктов его нет и быть не может.
4. **Scope creep** — оценено содержание РФП от 2016-06-10, а не то, чем проект окажется к концу.
