## 3. Special counts

No `A9` activity is crossed onto any element in this batch, so no measurable-target counts are due. `G2m / G3m / G4m` are crossed onto six stores; each gets a pre-load enumeration, with the reason per kind why it must arrive from the predecessor rather than be created at run time.

**A-008 — Configurable standards and business-rule set — 2 kinds → M**
1. *X-Customer Standard definitions* — validation has nothing to validate against until they exist; I-7 states they "will be defined as part of the project", i.e. settled before use, not authored by end users during operation.
2. *Business rules* — A-009 enforces at UI entry, import and assignment from the first record onward; an empty rule set would let the first import through unvalidated, contradicting G-12.4 "all records are validated upon import".

**A-073 — GIN record type and attribute model — 2 kinds → M**
1. *GIN records* — identifiers already allocated in the predecessor cannot be re-minted here without changing the identifier; they must arrive as data.
2. *Attribute definitions, including the industry-varying sets* — P-1 lets a record be created individually, by import, by wizard or by cloning; none of those paths can run before the attribute model that shapes the record exists.

**A-101 — Pre-defined levels: each, case, pallet — 3 kinds → M**
1. *each* — the base level of every hierarchy; P-11.3's fit check compares an item type to the next, so the lowest type must be present before any check can run.
2. *case* — the intermediate type the fit check compares against; without it "the next item type in the hierarchy" is undefined.
3. *pallet* — the top pre-defined type; P-11.1 declares the levels "pre-defined", i.e. present as reference data at start-up rather than authored during operation.

**A-114 — LN record type and attribute model — 2 kinds → M**
1. *LN records* — existing location numbers and their attributes live in the predecessor; re-issuing them would break the identifier already in external use.
2. *Attribute definitions, including the industry-varying sets* — L-1's four creation paths and A-120's "organised by various attributes" both presuppose the attribute model.

**A-120 — Unlimited-depth LN hierarchy organised by attributes — 2 kinds → M**
1. *Hierarchy definitions* — an existing location structure is a fact about the licensee's estate, not something re-derivable at run time; the system inherits it.
2. *Node placements (parent-child assignments)* — the depth is unlimited and the placement of each LN in the tree carries the predecessor's meaning; created fresh, the tree would be flat and the module unusable on day one.

**A-121 — Annual verification record — 1 kind → S**
1. *Prior verification events* — A-122's due-view answers "what is due" only by reference to when each record was last verified; before the first cycle completes here, that fact exists only in the predecessor, so an empty store would report every record as due or none.
