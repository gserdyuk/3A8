# 3. Special counts

**A-011 — Subscription entitlement model (view scope, export options)** · store · carries G2m / G3m / G4m.
Driver: entity kinds in the store that must be loaded from the predecessor applications.

Enumeration — 3 kinds, with per-kind reason why each must exist before the system is usable:

1. **Subscription** — a client's subscription is a pre-existing commercial relationship held in the predecessor applications; I-9 makes viewing and export depend on it, so with no subscriptions present at start-up no data consumer can view anything at all. It cannot be created at run time because the system has no act by which a client acquires a subscription in this batch.
2. **View-scope entitlement** — G-13.5 gates viewing on the subscription; the scope each existing subscription grants is a property of the pre-existing agreement, not something the running system derives, so it must arrive with the subscription or the gate has nothing to evaluate.
3. **Export-option entitlement** — I-9 makes the available export options subscription-dependent and D-5 names export to the General Requirements formats; which options an existing subscription carries is again a property of the prior agreement and must be present before any consumer can export.

**Not counted:** *access request with approval state* (D-2.1) — access requests are raised by consumers at run time through A-068 and decided through A-069, so this kind does not have to arrive from a predecessor. Arguable in one clause: if in-flight requests existed in a predecessor application they would have to be carried over, but no obligation in this batch says so, and I do not count on a guessed reading (P-6).

Count: **3** → special-count class **M**.
